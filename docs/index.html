Anthropic's Scion, rebuilt in the open. Your agents write code like kudzu grows.

Anthropic's monorepo outgrew git at 30,000+ merges a day, so they built Scion, and kept it internal. Kudzu rebuilds it from their write-up, in the open. Clients never clone the whole repo: they ask for exactly the objects they want through tiered caches. History, blame, diffs and merges run on the server, and changes land without a lock.

01 The problem

Git was built for people who go offline. Agents never do.

Every git clone is a full replica: all of history, packed and maintained on every machine. That's perfect for a laptop on a plane. It turns into a bottleneck when most clients are always-online agents and CI jobs, all landing into one monorepo.

Kudzu flips git's defaults

1

Always online

No full clone. The client asks the server for exactly the trees and blobs it wants, when it wants them.

2

Thin client, smart server

History, blame, diff, merge, rebase and commit run on the server. Clients cache objects, lay out files and notice edits.

3

A real source-control API

/api/log, /api/blame, /api/diff, /api/cat… CI and tools get answers without a checkout.

4

Scales out by caching

Objects are immutable and content-addressed, so any tier can answer. No packfiles, no repo maintenance.

5

Cheap, lock-free commits

A changeset is one append to a log. The ref moves separately, by a single-row compare-and-swap.

6

Sparse by default

The protocol is built around sparse checkout, and many reads and writes need no working copy at all.

02 How it flows

Ask for what you want. Every tier answers the same question.

Server, regional cache and node daemon all speak the same object RPC. Objects never change, so any tier can answer, and a miss travels upstream once, no matter how many agents asked.

  1. Agent A1 runs kudzu clone --sparse services/api. It resolves main to a root tree ID, then asks for exactly that one object. Every tier misses, so the want travels all the way up.

  2. From the root, A1 wants services/, and simply never asks for docs/ or tools/. Sparse checkout needs no special protocol: it's just not asking.

  3. services/api/ comes down; services/web/ is never requested. Each tier keeps a copy of what passes through it.

  4. With the trees in hand, A1 asks for every file it needs at once. Objects stream back one by one, so a dropped connection re-asks only for what's still missing. No multi-GB packfile.

  5. A2 on the same machine checks out the same path. Every object is a hit in node A's on-disk daemon. Nothing leaves the machine.

  6. B1 starts on a fresh machine. Its daemon misses, but the regional cache already has everything, so the server never sees the request.

  7. A change lands and all six agents want the new objects at the same moment. Each tier merges identical in-flight misses: six wants, one request to the server. In Kudzu's tests, 50 simultaneous cold requests reach upstream as 1.

03 Git vs Kudzu

Same job. Opposite assumptions.

Git puts a whole repository on every client and asks each one to do the work. Kudzu keeps the repository on the server and sends clients only what they ask for.

Comparison of git and Kudzu
TaskgitKudzu
Getting the code git clone copies a packfile with the full history to every client. The client asks for exactly the trees and blobs it wants, level by level. Sparse is just not asking.
History, blame, diff Computed on every client, from its own full copy. A server API backed by derived data. Works with no checkout at all.
Committing Commit locally, then push objects and history. Upload only the blobs the server is missing; the server creates the changeset. There is no push.
Landing A merge queue serializes landings behind a global lock. The server rebases onto the current tip and compare-and-swaps the ref. Lost the race? Retry.
Maintenance repack and gc on every mirror and replica. None. Immutable, content-addressed objects are served as-is by any cache.

05 Under the hood

A log of changesets. Everything else is derived.

A changeset doesn't point at a full tree. It lists the files it changed relative to its first parent, and becomes one entry in an append-only log. Root trees, path history, ancestry and blame are computed from that log by one recursive engine.

Append-only changeset log
  1. 1041web: fix nav focus ring2 files
  2. 1042api: tweak handler2 files
  3. 1043docs: add runbook1 file
{
  "parents": ["9e03d1f2…"],
  "author": "Alice <a@example.com>",
  "message": "api: tweak handler",
  "changes": [
    { "path": "services/api/handler.go",
      "mode": 33188, "blob": "<sha256>" },
    { "path": "services/api/old.go", "mode": 0 }
  ]
}

Creating a changeset is a single insert: no lock, no ref update. mode: 0 is a delete. Moving main is a separate compare-and-swap on one row.

derive engine value(key) = compute(key, parents' values)
  • root treeeager

    Checkout, diff, cat. Computed when the changeset is created, which also validates it.

  • generation + skip listeager

    Ancestry checks and main~N in O(log n) along the first-parent chain.

  • unodeeager · or lazy

    Path history. kudzu log <path> follows one chain, however much unrelated history is in between.

  • blamelazy

    Line ownership, computed on first query and cached for everyone after.

A new index is one more Deriver: a parents function and a compute function. The engine handles caching, computes missing ancestors oldest-first, and merges concurrent computations of the same key. Clients never see these structures, so they can change freely.

07 Quick start

Mirror a git repo and try it locally.

You need Go 1.24+, and git for the import. The import is incremental, so re-running it mirrors new commits.

  1. 1

    Install

    One binary runs the server, the caches and the client.

    go install github.com/garyships/kudzu/cmd/kudzu@latest
  2. 2

    Import git history

    Every commit becomes a changeset, with derived data computed as it goes.

    kudzu import --store ./data --git /path/to/repo --as main
  3. 3

    Start the three tiers

    Authoritative server, regional cache, and a per-machine daemon on a unix socket.

    kudzu server --store ./data --listen 127.0.0.1:7070 &
kudzu cache  --upstream 127.0.0.1:7070 --listen 127.0.0.1:7071 &
kudzu daemon --upstream 127.0.0.1:7071 --listen unix:///tmp/kudzu.sock &
export KUDZU_REMOTE=unix:///tmp/kudzu.sock
  4. 4

    Check out a slice, change it, land it

    commit --land creates the changeset on the server and lands it in the same call. -A also picks up new files.

    kudzu clone --sparse services/api $KUDZU_REMOTE wc
cd wc  # edit files…
kudzu status
kudzu commit -m "api: tweak handler" --land main
  5. 5

    Ask the server, no checkout needed

    History, path history, blame and diffs come straight from the API.

    kudzu log -n 5 --oneline
kudzu log services/api/handler.go
kudzu blame services/api/handler.go
kudzu diff --from main~3 --to main --stat
  6. 6

    Commit without a checkout

    Write files straight through the API and land them in one call.

    kudzu write -r main -m "bump version" --land main VERSION=@./VERSION

08 Built for AI agents

Version control your agents can just call.

kudzu mcp runs a Model Context Protocol server over stdio. Agents can query history, blame and diffs, and write and land changes, without a checkout. Add --read-only to let an agent look but not land.

More in Kudzu for AI agents, the Agent Skill, and llms.txt.

claude mcp add kudzu \
  -e KUDZU_REMOTE=unix:///tmp/kudzu.sock \
  -- kudzu mcp
{
  "mcpServers": {
    "kudzu": {
      "command": "kudzu",
      "args": ["mcp"],
      "env": { "KUDZU_REMOTE": "unix:///tmp/kudzu.sock" }
    }
  }
}
  • Ask, don't clone. History, blame and diffs are answered by the server from derived data.
  • Write and land in one step. Changes go straight to the server, which rebases and lands them lock-free.
  • Conflicts are data. A conflicting land returns the conflicting paths, so the agent can fix them and retry.

09 Roadmap

Early, and honest about it.

Kudzu is a working prototype with tests end to end. These pieces are not built yet.

  • Virtualized checkout

    FUSE files that fetch on first read. The protocol supports it; the client doesn't yet.

  • Auth & per-directory ACLs

    Today anyone who can reach the server can read and write.

  • Shared multi-server backend

    Metadata and objects already sit behind interfaces; running several servers needs Postgres/Spanner and S3/GCS implementations.

  • Object GC

    Changesets and objects orphaned by conflicts or lost races aren't collected yet.

  • Export back to git

    Import from git works, incrementally. Syncing back the other way doesn't yet.
